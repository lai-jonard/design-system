Agent design intelligence

A shared, evidence-backed decision system for Codex, Claude Code, Cursor, Antigravity, and future agents. It helps an agent understand the product job, select approved components and patterns, compose complete screens, test its decisions, and learn without silently rewriting design policy.

What we built

One shared system replaces duplicated agent instructions. Agent-specific files handle discovery; product and design decisions stay in repository-owned context.

Shared agent entry point

AGENTS.md gives every agent the same project map, constraints, authority order, build workflow, and approval boundary.

Thin native adapters

Codex, Claude Code, Cursor, and Antigravity discover the same canonical skill through their native folder and rule formats.

One product-design skill

Seventy overlapping project skills moved to a reference archive. One routed skill now loads only the canonical sources needed by the task.

Component intelligence

Every primitive, composed component, and page has API facts plus reviewable use, avoid, state, content, readiness, and alternative semantics.

Typography intelligence

Agents choose semantic roles such as page title, field label, metadata, and validation message; roles resolve to the existing token system.

Composition intelligence

Parent, child, adjacency, alternatives, state ownership, regions, and approved page patterns are queryable without duplicating canon.

Exemplars and evals

Three detailed exemplars preserve decisions worth repeating and mistakes to avoid. Six fixtures test retrieval, restraint, states, copy, and layout.

Reusable harness

Project-neutral schemas, validators, initialisation, evidence collection, review packets, and eval runners can seed the same workflow elsewhere.

Runtime

How an agent decides

Product truth and the explicit brief come first. Within design decision-making, approved intelligence is the primary source. The normal product-design workflow detects missing context and acts as a fallback—it does not overrule sufficient intelligence.

1Frame the jobUser, object, entry, exit, consequence, permissions, and scope.
2Retrieve intelligenceComponents, text roles, composition, exemplars, and product canon.
3Check readinessProve the approved context is sufficient before selecting a design.
4Compose the flowRegions, states, transitions, responsive behaviour, and accessibility.
5Render and inspectDesktop, narrow layouts, keyboard path, focus, states, and console.
6EvaluateDeterministic checks plus human correction count and quality review.
7Capture evidenceExact observation, provenance, candidate lesson, and counterexample.
8Approve learningA human accepts, narrows, edits, or rejects before canon changes.

Self-learning, governed

How the system improves safely

Annotated Figma screens, corrected diffs, reversions, review comments, failed evals, and model outputs begin as evidence—not rules. The best unit is a complete flow, annotated screen by screen, with reusable component lessons extracted afterwards.

LevelWhat it teachesPromotion boundary
FlowIntent, sequence, state transitions, consequences, permissions, recovery, and success.Primary unit for each learning cycle.
ScreenHierarchy, information priority, component composition, responsive transformation, and accessibility.One screen remains scoped evidence.
ComponentUse and avoid conditions, variants, content contracts, state ownership, and alternatives.Extract only after the lesson repeats.
Feature or sprintGroups product sources, approved designs, corrections, and outcomes.Review cadence, not a universal rule unit.

Highest-value example: original screen → human annotation → corrected screen → why the correction works → where it should not apply. A counterexample teaches the boundary as clearly as the preferred design.
