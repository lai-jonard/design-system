Development workflow

How to develop and contribute to the design system.

Local development

Run the full dev environment with a single command:

npm run dev

This starts three processes together:

  1. tsc --watch — recompiles TypeScript on save
  2. rollup --watch — rebundles dev/bundle.js when dist/ changes
  3. wds --root-dir=dev --watch — serves dev/ and live-reloads the browser

Save a .ts file and the browser reloads automatically within a couple of seconds.

Build chain

src/*.ts  --[tsc]-->  dist/*.js  --[rollup]-->  dev/bundle.js  --[wds]-->  browser reload
  • Source of truth: Lit components in src/
  • Never edit dist/ or dev/bundle.js directly — these are generated outputs
  • Docs pages load bundle.js as an IIFE (no ES module complexity in HTML)

One-off build

For commits or CI, run both steps:

npm run build && npm run build:bundle

Docs pages

Every component has a docs draft in dev/docs-drafts/la-<name>.html (output of /document) which is promoted to docs-src/components/la-<name>.html (the published Eleventy source) by /ready.

  • Open drafts at http://localhost:8000/docs-drafts/la-<name>.html while iterating
  • Each docs page loads ../bundle.js to register all components

Icons in docs pages

Every docs page <head> must include Phosphor CSS to register the icon font globally:

<link rel="stylesheet" href="../assets/vendor/phosphor/regular/style.css">
<link rel="stylesheet" href="../assets/vendor/phosphor/fill/style.css">
<link rel="stylesheet" href="../assets/vendor/phosphor/bold/style.css">

Inside Lit components, shadow DOM does not inherit page stylesheets. Any component using ph-* icons must import ${iconStyles} from '../styles/icons.js' and include it at the top of render(). Browsers cache the font — no extra network cost per component.

DialKit

dialkit/dialkit.js is a floating panel for live CSS variable tuning. Inject it into any docs page to tweak tokens in the browser without touching source files:

<script src="../../dialkit/dialkit.js"></script>

Override window.DIALKIT_DIALS before the script loads to customise which dials appear per page.

Adding a new component

  1. Create the .ts file in the appropriate folder:
    • src/primitives/ for base components
    • src/components/ for specialised components
    • src/pages/ for page-level components
  2. Export the component from src/index.ts
  3. Run /document <name> to generate a draft at dev/docs-drafts/la-<name>.html
  4. Build and verify:
npm run build && npm run build:bundle
  1. Open the draft at http://localhost:8000/docs-drafts/la-<name>.html to check rendering
  2. If the component is Tier 2 (specialised), log the rationale in design-language/components.md

Git & GitHub — the sprint pipeline

How work moves through the repo (decision 87). One maintainer, but three audiences: engineering reads the repo and PRs directly (WIP included — they finalise against the handoff document), QA/PM/stakeholders read the published mirror, and a second designer translates this work into a separate prototyping repo.

Sprint start

git checkout main && git pull && git checkout -b sprint-19-esignature

One branch per sprint, named for the sprint. Never reuse a branch after its PR merges.

During the sprint

Commit per decision-sized unit — a component, its docs, and its decision file travel together, message prefixed with the sprint:

git commit -m "s19: tinted ghost badges for signature status (decision 86)"

Push at least daily (backup + engineering can watch WIP). npm run dev keeps builds fresh while you work; the prebuild hook regenerates the token/motion mirrors automatically.

Sprint closeout checklist

  1. Heuristics sweep on the flow (design-language/usability-heuristics.md)
  2. /ready any new components → docs-src/ + handoffs/readiness.md rows
  3. Handoff doc version bump + changelog entry (handoffs/stage-N-*/)
  4. npm run build && npm run build:bundle && npm run docs
  5. python3 scripts/audit-prototypes.py — broken links / assets / orphans
  6. Commit, open the PR (gh pr create) with review pointers, merge
  7. Tag the handoff so it survives branch deletion: git tag sprint-19/handoff-v3.0 && git push --tags
  8. Publish the mirror when the docs are worth sharing: npm run publish:docs

What CI checks (GitHub Actions, every PR)

  • Generated files are fresh — CI rebuilds (build, build:bundle, docs) and fails on any diff. If it fails: run step 4 above and commit the result.
  • Prototype audit — no broken navigation links or missing assets in dev/prototypes/.
  • No real company names in prototype/docs markup. Documented scoped exceptions carry a no-real-names-ok marker on the same line.

CI owns the mechanical invariants only. Decision logging, handoff versioning, heuristics reviews, and PR bodies stay manual — they are the design work itself.

The published mirror

npm run publish:docs builds the site, rewrites paths, and pushes to the Pages mirror (lai-jonard/design-system) — a deliberate manual step, because the mirror is a curated share surface for QA/PM/stakeholders. handoffs/, decisions/, and CLAUDE.md never ship to it. It's fine to publish daily; it's a reference, not a release.

The correction loop — where feedback gets written down

Every correction the designer makes to AI-drafted work (or to their own earlier work) first lands as evidence in .agent-system/evidence/inbox/, with provenance and the observed fact separated from any proposed generalisation. Drafts carry an explicit "open taste questions" list wherever the author wasn't sure.

The evidence collector builds a review packet; it never edits canonical guidance. A human decides whether an item is one-task evidence, a scoped preference, a reusable pattern, a rule, or a rejection. Only accepted items are routed below. This keeps the memory durable without turning one comment, screenshot, or model output into policy.

Routing after human acceptance — by what kind of correction it is:

The correction is… It gets written to Example
A settled rule ("never X", "always Y") decisions/NN-*.md + the relevant design-language/ doc Tinted ghost badges for status (decision 86)
A rule that will be cited, enforced, or tested Also add an entry to design-language/rules.md (stable rule/… ID) rule/one-card-surface (decision 89)
A rule a machine can check A check in scripts/design-audit.py + a fixture in tooling/evals/ rule/no-hardcoded-values
A screen/flow composition pattern (how to build) The narrowest relevant design-language/ document, normally page-architecture.md plus the specific surface doc How a document-first review header is composed
Copy or vocabulary design-language/copy-guidelines.md Signature-status vocabulary
Taste or preference (not yet a rule) design-language/design-brief.md § Taste Space over chrome; evidence over labels
Business context or goals design-language/design-brief.md Who the buyer is; what's deferred
A mistake worth remembering (ours or an agent's) .agents/skills/product-design/exemplars/pr-*.md fill-mode: both trapping a fixed backdrop
A decision we can't make yet .agents/skills/product-design/coverage-gaps.md (with an owner) Ceremony failure state — unspecified by HQ
How an agent should approach the work (mode, routing) .agents/skills/product-design/SKILL.md Copy mode must not widen into a redesign
Workflow / process This file's Decisions & evolution section (+ decisions/ if load-bearing) Branch-per-sprint (decision 87)
Session-level working preference The current agent's local memory only; never canonical without review Preferred dev commands

Rule of thumb: if a future draft would repeat the mistake without the note, it must be written down — in the most specific home that a future author (human or AI) will actually load when doing that kind of work.

Never promote one screenshot, one shipped file, or one comment into a universal rule. A rule earns an ID and a check once it has survived being applied more than once; until then it's taste (design-brief.md) or an open gap (coverage-gaps.md). See decision 90.

Decisions & evolution

How the workflow itself has changed over time. Each entry: the rule, why it exists, and how to apply it. Promote to a dedicated file if this section exceeds ~10 entries.

One governed product-design harness across agents — 2026-07-27

Full architecture and rationale in decision 91.

Why: Claude-only bootstrap content, 71 overlapping discoverable skills, and duplicated LawAdvisor guidance created retrieval noise and agent-specific drift. Direct self-learning would replace that drift with a more dangerous failure: unreviewed observations becoming policy.

How to apply: Keep AGENTS.md as the shared map and product-design as the single entry point. Adapters stay thin. Capture corrected diffs, comments, eval failures, and Figma annotations in the evidence inbox; generate a review packet; update canonical sources only after human acceptance. Use the portable harness to install the same workflow in other projects, then supply that project's own context and fixtures.

Git standard: branch-per-sprint, PR-even-solo, tagged handoffs — 2026-07-24

Full pipeline in the "Git & GitHub" section above; rationale in decision 87.

Why: Solo maintenance made ceremony easy to skip — a stale-named branch carried unrelated PRs, sprints landed as single 70-file commits, and generated files went stale whenever a build step was forgotten. The failure modes were mechanical, so the fix is mechanical: naming rules, a checklist, and CI for the invariants.

How to apply: Branch per sprint; commit per decision-sized unit with an sNN: prefix; PR + tag at closeout; let CI catch stale generated files, broken prototype links, and real-name leaks. Keep judgement calls (decisions, handoffs, heuristics) manual.

Solves are for composed components and flows, not primitives — 2026-04-24

Primitives (src/primitives/) skip straight to /build → /audit → /ready plus atomic decisions/NN-*.md. Composed components (src/components/) and flow/page work get a preceding solves/yymmdd-N-topic/ workspace when the problem is still mushy.

Why: Primitives are narrowly scoped — the questions are atomic ("what weight, what radius, what reflects"). A three-file solve workspace is overkill for a decision that fits in three lines. Composed components and flows span multiple screens and interactions; that shape needs a workspace.

How to apply: If the problem fits one primitive and you can state the decision in a sentence, go straight to decisions/ once it's locked. If the problem spans multiple components, touches UX flow, or needs iteration through drafts, open a solve first. Distilled conclusions get promoted from the solve to decisions/ as they firm up.

Published vs dev — the docs site is the source of truth — 2026-04-24

A component is published when it has JSDoc in source, a page in docs-src/components/, an entry in design-language/components.md, and a row in handoffs/readiness.md. Pre-publish work lives in dev/docs-drafts/ and doesn't count yet.

Why: dev/ is the workbench — anything goes, iterate freely. docs-src/ is the public surface engineering and product read. Without a clear line between the two, stale demos get treated as spec and drift accumulates. The line is: "does it appear on the docs site when I run npm run docs?" If yes, it's published.

How to apply: Components graduate from dev/docs-drafts/ to docs-src/components/ when they pass the /ready gates. Before that, they're WIP and not for external reference. Unrelated to npm publish — this is the docs-visibility bar.

Prototype publish gate — 2026-04-24

Prototypes (flow/page mockups in dev/prototypes/) move into the published docs site (/founder-flow/*.html and equivalent) only after passing every gate in prototype-standards.md.

Why: Prototypes are engineering's structural source of truth during handoff — layout, composition, spacing, interactions. That only works if a published prototype is guaranteed to use only published components, style only through tokens, and respect the same standards we apply to components. WIP prototypes demoed as reference lead to drift.

How to apply: While iterating, keep prototypes in dev/prototypes/<flow>/. When ready to publish, walk the 8-gate checklist in prototype-standards.md. When it passes, add the file to the passthrough list in .eleventy.cjs and run npm run docs. Anything blocked by an unpublished component waits — publish the component first.

Component docs: stage in dev/docs-drafts/, publish on /ready — 2026-04-24

/document writes draft docs pages to dev/docs-drafts/la-<name>.html as standalone HTML. /ready (Gate 9) verifies the draft exists, promotes it to docs-src/components/la-<name>.html in Eleventy-template form, updates the catalogue chip and href, and flips readiness to 🟢. The draft file is deleted after the promotion lands.

Why: dev/ is the workbench, docs-src/ is the published surface. A draft sitting in docs-src/ would already appear on the served site, which muddies the "published" boundary the rest of the workflow relies on. Staging preserves that boundary — drafts are visible under npm run dev but hidden from the built docs site until /ready runs.

How to apply: After /build, run /document <name> to draft the docs page — it lands in dev/docs-drafts/. Iterate on the draft there (viewable at http://localhost:8000/docs-drafts/la-<name>.html under npm run dev). When ready, run /ready <name> — it runs the 9 gates, promotes the draft to docs-src/, updates the catalogue, flips readiness. Then npm run docs to rebuild the site.
